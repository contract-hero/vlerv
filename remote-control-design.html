Remote Control

Beam (v1): send an artifact from one Vlervcode instance to another with one link — peer-to-peer, end-to-end encrypted, no VPN, no hosting.
Scope (v2): a persistent paired session — browse and live-follow the artifacts open on another machine's Vlervcode, and drive it remotely.

status: v1 (Beam) merged · v2 (Scope) proposed transport: iroh (QUIC, hole-punched) platforms: macOS · iOS (planned)

1 · Summary

Vlervtifacts is deep-link addressable, live-reloading, and read-only — on one machine. This design extends all three properties across machines. The transport is iroh, a Rust P2P library that gives every app instance a cryptographic identity (an ed25519 NodeId) and dials direct, end-to-end-encrypted QUIC connections between instances by hole-punching through NATs, with encrypted public relays as fallback. No VPN to configure, no server that stores content, no public URL that exists.

Two features ship on that foundation, in order:

  • Beam (v1) — a one-shot, content-addressed artifact transfer. The sender's share popover produces a ticket wrapped in a vlerv://receive?ticket=… deep link. It travels over any channel you already use (Slack, iMessage, AirDrop of a text snippet). The receiver clicks it, confirms, and the artifact streams in — integrity-verified by its BLAKE3 hash — and opens in a tab.
  • Scope (v2) — a durable pairing between two instances. A paired peer shows up as a sidebar drawer: its open tabs, bookmarks and recents, fetchable on demand, with live reload bridged across the wire. A control-scoped peer can also push: open an artifact on the remote instance — the literal "remote control".

Everything reuses the app's existing load-bearing machinery: the security.rs RootSet gate guards every remote read, the watcher bus drives cross-machine live reload, the sandboxed-iframe pipeline renders remote content exactly as untrusted as it renders local content, and deeplink.rs grows new verbs it was already structured to receive.

2 · Problem & constraints

The user runs Vlervcode on more than one Mac, and occasionally wants a colleague to see an artifact. Today the options are bad: a VPN or Tailscale-style overlay (setup, a system-level agent, an ongoing trust decision), or uploading the artifact to a hosting service (the artifact becomes a public-ish URL on someone else's infrastructure). Both violate the product's nature — local files, private by default, zero services.

Hard constraints

ConstraintConsequence for the design
No VPN / overlay network setupConnectivity must be application-level: NAT traversal built into the app itself.
No public hostingContent never rests on a server. Any intermediary may carry only ciphertext, transiently.
End-to-end privateEncryption keys live only in the two app instances. Relay operators see connection metadata, never content.
Read-only product (PRODUCT.md principle 4)The remote API exposes reads only. The one write the app performs — persisting a received artifact — stays inside its own state directory, ~/Library/Application Support/Vlerv/.
The webview is privileged; artifact content is untrustedAll networking lives in the Rust core. The webview gains IPC commands, never network capability. Received content enters the existing sandboxed render pipeline.
No telemetry, local-firstThe networking stack boots lazily — the app makes zero network connections until the user invokes a remote feature.

Posture change. This is the app's first networked feature. Today Vlervcode dials nothing. The lazy-boot rule above is not an optimization — it is the contract that keeps "local-first" true: no beam, no scope, no sockets.

3 · Approach: why iroh

Candidates evaluated against the constraints:

OptionNo VPNNo hostingE2E privateFits the stackVerdict
iroh (embedded Rust library: QUIC + hole-punching + encrypted relay fallback)✔✔ relays carry ciphertext transiently✔ keys are the two NodeIds✔ native Rust, embeds in the Tauri coreChosen
Tailscale / WireGuard overlay✘ it is the VPN✔✔system-level agent, per-machine onboardingExcluded by constraint
Cloudflare Tunnel / ngrok + auth✔✘ traffic terminates at the provider; a public URL exists✘ TLS terminates at the edgeexternal daemonRejected
WebRTC data channels✔✔ (STUN/TURN)✔ (DTLS)heavy C/C++ deps or immature Rust bindings; signaling server to build and run ourselvesWorkable but more moving parts than iroh for the same result
Syncthing-style folder sync✔✔✔syncs directories, not sessions — solves replication, not "what is open over there"Different feature; revisit for workspace mirroring someday
Custom relay server + E2E crypto✔△ we'd run the relay✔ if we build it rightwe own NAT traversal, framing, crypto reviewReinventing iroh, worse

iroh wins on fit: it is a Rust library, so it compiles into the existing Tauri binary; identity, encryption, NAT traversal, connection lifecycle and content-addressed blob transfer (iroh-blobs) are all solved layers; and its sendme tool is a working reference implementation of exactly Beam's shape. n0 operates free public relays; the relay URL is a config field, so a self-hosted iroh-relay remains an escape hatch if the trust calculus ever changes.

Version pin. iroh is on its 1.0 release line but the API churned significantly through 0.x. Pin an exact version in Cargo.toml, wrap all iroh types behind our own remote::endpoint module boundary, and treat upgrades as deliberate migrations.

4 · Shared foundation

Both features stand on one new backend subsystem, src-tauri/src/remote/:

src-tauri/src/remote/
├── mod.rs        // feature façade; lazy boot; Tauri command handlers
├── endpoint.rs   // iroh Endpoint + Router lifecycle; identity persistence
├── beam.rs       // v1: stage / serve / fetch one artifact (iroh-blobs)
├── scope.rs      // v2: session protocol server + client
├── peers.rs      // v2: trusted-peer store, pairing, scopes, revocation
└── proto.rs      // wire types (serde + postcard), protocol version consts

Identity

On first use of any remote feature, the app generates an ed25519 keypair and persists the secret key at ~/Library/Application Support/Vlerv/remote/identity.key (mode 0600). The public half is the instance's NodeId — its stable, dialable address. Each install gets its own identity; a human-readable device name (default: the Mac's hostname) travels in every handshake.

Endpoint lifecycle

  • Lazy boot. The endpoint starts on the first beam/scope action, or at launch only if the peer store is non-empty and the (new) preferences.remote_listen flag is on. Otherwise: zero sockets.
  • One endpoint, two protocols. An iroh Router multiplexes by ALPN: iroh-blobs' own ALPN for content transfer, and vlerv/scope/0 for the v2 session protocol. Bumping the trailing integer is the protocol-break mechanism.
  • Firewall reality. An unnotarized app accepting inbound connections triggers the macOS application-firewall prompt on some setups. Document it; outbound-initiated (dial-out) flows — which is all of Beam from the receiver's side — do not.

One security gate, reused

Every path that a remote peer can cause this app to read flows through the same security::canonicalize_and_check_root gate that local IPC already uses. Remote access never widens the readable set — it can only see what the local UI could see, filtered further by per-peer scope (§6). This is the single most important line in the design.

5 · v1 — Beam

One artifact, one link, one click. Beam is deliberately session-free: no pairing, no persistent state on either side beyond the received file. It exists to make "send this report to my laptop / to a colleague" cost three seconds.

Sender flow

  1. The share popover (next to the existing share-sheet and Open-in-Slack buttons in Toolbar.tsx) gains "Beam to Vlervcode…". Also available from file-row context menus and as vlerv beam <path> in the CLI.
  2. The backend canonicalizes the path through the share module's existing resolve_paths policy (external files shareable on purpose, same as the share sheet), stages the file into an iroh-blobs store, and computes its BLAKE3 hash.
  3. It boots the endpoint if needed and mints a blob ticket: node address info + hash + format, serialized as one URL-safe string.
  4. The frontend receives { ticket, link } where link is 
    vlerv://receive?ticket=<blob-ticket>&name=report.html&size=482133
    and offers: copy link, native share sheet, Open in Slack. name/size are display hints for the receiver's confirm dialog — the ticket's hash, not the hints, is the truth.
  5. The sender keeps serving while the app runs. A small "beaming" indicator lists active offers with fetch counts and a Stop action (instant revocation — the ticket dies with the offer).

Receiver flow

  1. The deep link arrives through the existing LaunchServices → deeplink.rs route. A new Receive { ticket, name, size } intent joins Open/Reveal (the parser's UnknownVerb/NotYetImplemented errors were built for this day).
  2. A confirm dialog shows: file name, size, the sender's NodeId fingerprint (and device name once connected), and where the file will land. Nothing transfers before confirmation — a hostile link can't make the app fetch.
  3. On accept, the app dials the ticket, streams the blob with verified chunks (BLAKE3 — a corrupted or substituted stream fails, it cannot render), and writes it to 
    ~/Library/Application Support/Vlerv/received/2026-08-15/report.html
  4. The file opens in a tab through the normal pipeline, marked with a beamed badge (sibling of the existing external badge). A "Received" entry point lists past beams. The read-only principle holds: the app wrote inside its own state dir, never in the user's tree.

Semantics & edge cases

CaseBehavior
Sender quits before fetchFetch fails with a clear "sender offline" state; the receiver can retry from the same dialog when the sender is back. A ticket is an offer, not an escrow.
File changes after stagingThe ticket pins the hash at mint time — the receiver gets exactly what the sender saw. Re-beam to send the new version (cheap: re-hash + new ticket).
Ticket forwarded to a third partyCapability semantics: possession grants fetch, like a secret link. Mitigations: offers default to a 24 h TTL and an optional single-fetch mode; Stop revokes instantly; v2 adds lock-to-peer beams.
Artifact with relative assetsv1 ships single-file only (the self-contained-HTML convention makes this the common case). A follow-up uses iroh-blobs collections to beam a file set as one ticket.
Oversized contentReuse the reader's existing size-cap philosophy: warn above 20 MiB, hard-cap at 256 MiB for v1.
No Vlervcode on the receiving endOut of scope, deliberately: the feature's charm is instance-to-instance. The ticket string still works with sendme receive for emergencies, since the blob protocol is standard.

6 · v2 — Scope

A periscope into your other machine's reading room. Scope turns the one-shot trick into a relationship: two instances pair once, then either can browse what the other has open, follow along live, and — with permission — drive it.

Pairing

  1. On the host: Settings → Remote → "Pair a device…" shows a pairing ticket (node address + one-time pairing token) as a QR code and a copyable vlerv://pair?ticket=… link. This is finally a concrete reason to mount the Settings surface that PRODUCT.md lists as an open decision.
  2. The other instance opens the link (or scans the QR with the Mac's camera — nice-to-have). Both machines display the same six-word fingerprint derived from a hash of both NodeIds; the user confirms it matches on both screens. This kills man-in-the-middle at pairing time in a way a human can actually verify.
  3. Each side persists the other in ~/Library/Application Support/Vlerv/remote/peers.json: NodeId, device name, granted scope, paired-at, last-seen. Revocation is deleting the entry — the scope server rejects non-peer NodeIds at the handshake, so revocation is immediate.

Scopes — what a peer may do

ScopeGrantsDefault for
view-openList open tabs, bookmarks, recents; fetch exactly those artifacts; subscribe to their change events.A colleague's paired instance
browseview-open + walk the workspace tree and fetch any file the RootSet admits (same ignore/hidden/symlink policy as ⌘P's list_files_recursive).Your own second machine
controlbrowse + push: open/focus an artifact on the host, toggle its reader mode. The literal remote control — drive the Studio's big screen from the sofa laptop.Opt-in, own machines only

Wire protocol

One QUIC bi-stream per session under ALPN vlerv/scope/0, length-prefixed postcard frames of a versioned serde enum. Content never rides the control stream: GetArtifact answers with a BLAKE3 hash, and the bytes move over the iroh-blobs protocol — verified, resumable, deduplicated (an artifact fetched twice, or beamed earlier, costs nothing the second time).

// proto.rs (sketch)
enum Req  { Hello { proto: u32, device: String },
            ListTabs, ListBookmarks, ListRecents, ListTree { path: String },
            GetArtifact { path: String },        // → ArtifactMeta { hash, size, mtime }
            Subscribe,                           // → server starts pushing Event frames
            OpenOnHost { path: String, reader_mode: bool } }  // control scope only

enum Event { TabOpened { path }, TabClosed { path }, TabActivated { path },
             FileChanged { path, hash },         // re-render trigger + new content addr
             FileRemoved { path } }

Host side: bridging app state to the wire

Two sources feed the scope server, one per direction of the existing architecture:

  • Filesystem truth (already in Rust). The watcher's events — the same stream that becomes vlerv://file-changed — additionally fan out to subscribed peers as Event::FileChanged, with the file re-hashed so the event carries the new content address.
  • Session truth (lives in React). The tabs reducer (src/state/tabs.ts) is the authority on what is open. A thin effect publishes the open-tab list to the backend (remote_publish_tabs command) on every commit — the same shape the app already persists into panes.tabs. The backend caches it for ListTabs and diffs it into TabOpened/Closed/Activated events.

Every GetArtifact and ListTree passes through security::canonicalize_and_check_root plus the peer's scope filter before a single byte is read.

Client side: the remote drawer

A paired peer that is online appears as a fourth sidebar drawer — "Remote: Mac Studio" — alongside Bookmarks / Recent / Files, built from the same SidebarSection shape. It lists the peer's open tabs (live), and under browse scope, a lazy tree. Presence (online/offline, connecting) shows in the drawer header.

Opening a remote entry creates a tab whose address is vlerv-remote://<peer-id>/abs/path. The fetch lands in a content-addressed cache (remote/cache/<hash>), and the render pipeline consumes it exactly like a local FilePayload — sandboxed iframe, injected <base href> disabled for remote (no relative-asset resolution against a machine that isn't there), zoom, scroll memory keyed by tabId::address, all for free.

Live reload crosses the wire. An incoming FileChanged re-fetches by new hash and injects a synthetic event into the watcher bus (src/state/watcher-bus.tsx) — the debounce, tab-reload and scroll-restoration machinery downstream doesn't know or care that the file lives on another Mac. Watching Claude rewrite a report on the other machine, live, with scroll position held: that is the demo.

Follow mode. One toggle on the drawer: the local instance mirrors the host's active tab, switching as it switches — a presentation mode for pair-reading a review with a colleague, or for using the laptop as a teleprompter of the Studio.

Why this is the "definitive feature". Each of the product's three positioning properties extends across machines: deep-link addressability (tickets and pair links are vlerv:// URLs), live reload (FileChanged crosses the wire into the same bus), and the read-only tree (scopes + RootSet). Nothing new is bolted on; the existing identity of the app is what gets networked.

7 · Security & threat model

ThreatMitigation
Relay operator (n0) reads contentImpossible by construction: QUIC session keys derive from the two endpoints' keys; relays forward ciphertext. Residual: connection metadata (who talked to whom, when, volume). Escape hatch: self-hosted iroh-relay, URL in preferences.
Beam ticket leaks (forwarded Slack message)Capability semantics are the design, not a bug — but bounded: default 24 h TTL, optional single-fetch, instant Stop, and (post-pairing) lock-to-peer beams that check the fetcher's NodeId.
Hostile vlerv://receive link (drive-by fetch)No fetch before an explicit confirm dialog showing sender fingerprint, name, size. Parser hardening (strict percent-decoding, null-byte rejection) already exists in deeplink.rs.
Malicious artifact contentUnchanged trust model: artifact content was always untrusted. Sandboxed iframe, SVG script-stripping, image caps — remote content enters the same pipeline with the same badge-level provenance UI.
Pairing man-in-the-middleOne-time pairing token in the ticket + mutual six-word fingerprint confirmation on both screens before the peer is persisted.
Stranger dials the scope portHandshake rejects any NodeId not in peers.json before any request is parsed. QUIC itself already authenticated the NodeId — there is nothing to spoof.
Path traversal via GetArtifact/ListTreeThe same canonicalize_and_check_root gate as local IPC, then the scope filter. Symlink/hidden/ignore policy identical to ⌘P's walker. Error wording reuses the no-existence-leak convention from the share module.
Abuse of control scopecontrol can only invoke the same intents a deep link can (open, reveal, reader mode) — it inherits the deep-link security posture, including RootSet classification. It cannot read results, write, or execute.
Resource exhaustionPer-peer concurrent-stream and bandwidth caps; 20 MiB soft / 256 MiB hard size caps; subscription fan-out is bounded by the peer count, which is bounded by the human who paired them.
Identity key theft (disk read)Key file mode 0600 inside the app's state dir. Future hardening: move the secret to the macOS Keychain. Revocation from the other side is deleting the peer entry.

Deep-link verbs

vlerv://receive?ticket=…&name=…&size=… (v1), vlerv://pair?ticket=… (v2). Both added to DeepLinkIntent with the same strict parsing and tests as open/reveal.

State & config

New keys under the existing settings schema: preferences.remote_listen: bool (default false), preferences.relay_url: string | null (null = n0 defaults), preferences.beam_ttl_hours. New files under Application Support/Vlerv/remote/: identity.key, peers.json, blobs/, cache/, received/.

Dependencies

iroh, iroh-blobs, postcard (plus existing serde). Binary-size impact expected in the several-MB range — acceptable for a local .app; measure at M1 and record in STATUS.md.

Frontend

src/state/remote.tsx (peers, presence, offers), src/components/RemoteDrawer.tsx, BeamDialog.tsx (send + receive faces), a beamed badge in the toolbar, share-popover and context-menu entries, and the Settings → Remote pane. CLI grows vlerv beam <path> and vlerv receive <ticket>.

10 · Risks & open questions

Risks

RiskMitigation
iroh API churn around its 1.0 lineExact version pin; all iroh types quarantined behind remote::endpoint; upgrades are deliberate PRs.
Dependence on n0's public relay infrastructureDirect connections are the common path; relay is fallback; relay_url preference enables self-hosting the day it matters.
Both instances must be running (no daemon)Accepted for v1/v2 — the product is an app, not a service. A menu-bar residency mode is a possible v3 if "sender offline" stings in practice.
First networked feature enlarges the audit surfaceNetworking confined to the Rust core; webview gets commands, not sockets; scope server unreachable except from paired NodeIds; run the security-review skill over the remote/ module before each merge.
Unnotarized app vs. macOS application firewallDocument the prompt; all Beam-receiver traffic is dial-out and unaffected.

Open questions

  • Received-artifact visibility. Keep received/ only behind the Received list, or also surface it as a pseudo-entry in the sidebar? (Leaning: a drawer entry appears only while received tabs exist.)
  • Default TTL. 24 h proposed; the right number is whatever makes a forwarded stale link useless without making "fetch it tomorrow" annoying.
  • Default scope for own-machine pairing. Should the pairing flow offer a "this is my own machine" toggle that grants browse+control in one step?
  • Fingerprint wordlist. PGP word list vs. EFF short list vs. emoji. Bikeshed, but a fun one.
  • Naming. "Beam" and "Scope" are working names; the vlerv:// verbs (receive, pair) are the actual frozen API — chosen to stay meaningful if the feature names change.

11 · Beyond v2

Not designed here, but the foundation makes them cheap to imagine:

  • iOS companion — the committed next platform. A read-only phone reader for artifacts whose entire data layer is this design: the phone owns no files, so it pairs as a view-open/browse Scope client and receives Beams. The stack carries over — Tauri 2 targets iOS from this same React + Rust codebase, and iroh compiles for iOS, so the remote/ module ships to the phone unchanged. Distribution can stay personal (sideload or TestFlight; no App Store). Now unblocked: Beam (v1) is merged, so the remote foundation exists; the iOS app's remaining prerequisite is Scope (v2), which gives the phone the paired-session browse/live-follow it reads over. PRODUCT.md now records macOS and iOS as the product's two platforms (this doc previously asked for that revision), so the macOS-only constraint is no longer in the way.
  • Co-reading. Scroll-position sharing over the session stream — a laser pointer for pair-reviewing an audit, two machines, one scroll.
  • Collections. Beam a directory (an HTML report with assets, a whole learning module) as one ticket via blob collections.
  • Locked beams by default. Once most beams flow between paired machines, flip the default from capability-link to peer-locked.
  • Menu-bar residency. A headless serve mode so the Studio answers fetches without the window open.
  • Agent-to-remote deep links. A Claude Code session on the Studio ends with a link that opens the artifact on whichever paired machine you're holding — vlerv://open?path=…&on=macbook. The deep-link scheme becomes location-transparent.
Explicit non-goals
  • Web viewer / browser fallback. Receiving requires Vlervcode. A web viewer means hosting, which is the thing this design exists to avoid.
  • Multi-user collaboration / presence for strangers. The product has one user and their colleagues-of-the-moment; there is no roster, no accounts, no cloud identity — NodeIds and a peers file are the whole social graph.
  • Remote editing. Read, do not edit — now over the network too.
